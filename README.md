# Smart Bus Transit Ecosystem

A Turborepo monorepo containing three independent PWAs (Passenger, Conductor,
District Admin) on a shared Supabase/PostgreSQL/PostGIS backend. See
[ARCHITECTURE.md](./ARCHITECTURE.md) for the data-flow, realtime, and
security-model deep dive, and the [Final Audit](#final-audit) below for a
requirement-by-requirement status table.

## 1. Project Overview

- **Passenger PWA** (`apps/passenger`): zero-login rider app — geolocation →
  nearest stop (PostGIS) → route/bus search with passed-origin filtering →
  live GPS tracking → mock checkout → signed QR ticket → destination
  geofence notification.
- **Conductor PWA** (`apps/conductor`): government-ID login → Wake Lock +
  high-accuracy GPS broadcast every 3-5s → Presence → Pocket Mode →
  BarcodeDetector/ZXing QR scanner → atomic ticket validation → occupancy →
  stop progression → long-press SOS.
- **District Admin PWA** (`apps/admin`): Supabase email/password login →
  CRUD for stops/routes/route-stops/fares/buses/conductors/schedules → CSV
  bulk import with preview/validation → scheduling calendar → live fleet
  map (Presence) → SOS command center (Postgres Changes + alarm).

## 2. Architecture

```text
apps/passenger, apps/conductor, apps/admin   — independent Vite+React PWAs
packages/shared-types                        — domain types, RPC/realtime contracts
packages/ui                                  — Tailwind component library
packages/supabase-client                     — Supabase client, auth, RPC/realtime helpers
supabase/migrations                          — schema, PostGIS, RLS, RPCs
supabase/functions                           — Edge Function (conductor provisioning)
supabase/seed.sql                            — demo transit network
```

Full details: [ARCHITECTURE.md](./ARCHITECTURE.md).

## 3. Prerequisites

- Node.js ≥ 20, npm ≥ 10
- A [Supabase](https://supabase.com) project (free tier is sufficient) —
  PostGIS is enabled via migration, no manual dashboard step needed
- [Supabase CLI](https://supabase.com/docs/guides/cli) for running
  migrations/seed/Edge Functions locally or against your project
- A modern Chromium-based browser for full feature coverage (BarcodeDetector,
  Wake Lock) — see [Browser Compatibility](#browser-compatibility)

## 4. Installation

```bash
npm install
cp .env.example .env
```

Edit the root `.env` with your Supabase project's `VITE_SUPABASE_URL` and
`VITE_SUPABASE_ANON_KEY` (Project Settings → API in the Supabase dashboard).
All three apps read this single file — each `apps/*/vite.config.ts` sets
`envDir: "../../"` so there's nothing to keep in sync across apps.

## 5. Supabase Setup

```bash
supabase login                                    # or: supabase login --token <personal-access-token>
supabase link --project-ref <your-project-ref>
supabase db push                                  # applies supabase/migrations/*.sql in order
supabase db query --linked -f supabase/seed.sql   # loads demo data (CLI ≥2.x; older CLIs use `db execute -f`)
supabase functions deploy provision-conductor
supabase secrets set SUPABASE_URL=<project-url> SUPABASE_SERVICE_ROLE_KEY=<service-role-key>
```

On a fresh/empty project, `supabase db reset --linked --yes` is a faster way
to apply all migrations from scratch if `db push` ever fails partway through
(it drops and recreates the remote schema — only use it on a project with no
real data yet).

**Note on pgcrypto**: Supabase installs `pgcrypto` (and other extensions)
into the `extensions` schema, which is not always on every role's
`search_path`. The RPCs in migration 008 schema-qualify calls like
`extensions.gen_random_bytes()` and `extensions.hmac()` for exactly this
reason — if you add new pgcrypto-based SQL, qualify it the same way rather
than assuming an unqualified call will resolve.

After migrations run, set the real ticket-signing secret (a placeholder
random value is auto-generated by migration 008, but rotate it once):

```sql
update app_secrets set value = encode(extensions.gen_random_bytes(32), 'hex')
where name = 'ticket_qr_hmac_key';
```

Create your first admin account (Supabase Dashboard → Authentication → Add
user, e.g. `admin@transit.gov`), then promote it:

```sql
update profiles set role = 'admin' where id = '<the new user''s UUID>';
```

Conductors are provisioned from the Admin PWA (**Conductors → Add
conductor**), which calls the `provision-conductor` Edge Function + the
`link_conductor_account` RPC — see [ARCHITECTURE.md](./ARCHITECTURE.md#key-assumptions-documented-per-rule-11).

### Local development

Running fully offline against the Supabase CLI's local stack
(`supabase start`) works the same way — point `.env` at the local API URL
and anon key printed by that command, then run the same `db push`/seed/
`functions serve` commands against it.

**Manual end-to-end test** (Passenger → Conductor → Admin):

   (grants Wake Lock + GPS), confirm the trip shows `ACTIVE`.
3. Passenger: open the app, allow location, pick the same route/origin/

4. Passenger: buy a ticket (mock payment), confirm the QR renders.
5. Conductor: open **Scan tickets**, scan the passenger's QR, confirm it's
   accepted and occupancy increments; scan it again and confirm rejection.
6. Conductor: mark the destination stop **Departed**, confirm the

7. Conductor: long-press **SOS**, confirm it appears instantly in Admin →

## 14. Deployment

Deploy each app as a **separate static site** (they are independent Vite
builds with independent manifests/service workers) — e.g. Vercel/Netlify/
Cloudflare Pages, one project per `apps/*` with build command
`npm run build --workspace=@sbt/<app>` and output directory `apps/<app>/dist`.
Set each project's `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` env vars in
the hosting provider — never commit real `.env` files. Deploy
`supabase/functions/provision-conductor` via `supabase functions deploy`
separately; it is not part of any app's static build.

## 15. Browser Compatibility

| Feature | Support | Fallback / limitation |
|---|---|---|
| Geolocation API | All modern browsers | Manual stop selection if denied/unavailable |
| Wake Lock API | Chromium (desktop/Android), Safari 16.4+ | GPS tracking continues even if Wake Lock fails/unsupported |
| BarcodeDetector | Chromium only | `@zxing/library` fallback (all browsers) |
| Notification API (foreground) | All modern browsers | Used for the geofence "Have you alighted?" prompt |
| Background Web Push | Not implemented | Would require a VAPID push server; out of scope — see `usePushNotifications.ts` |
| Service Workers / PWA install | All modern browsers; iOS Safari has the most restrictions | iOS requires PNG icons (see §13) |
| Background JS execution | **No browser guarantees this** | Pocket Mode maximizes foreground reliability but cannot promise telemetry continues once the OS suspends a backgrounded/locked tab |

## 16. GPS Limitations

GPS is inherently noisy; this repo does not pretend otherwise:
- Passenger live map interpolates (`requestAnimationFrame` lerp) between
  broadcast points instead of teleporting the marker, and flags telemetry
  "stale" after 15s of silence.
- Conductor telemetry throttles broadcasts to the 3-5s band and skips
  points that haven't moved ≥3m, to control both bandwidth and battery.
- The geofence-alighting check polls (`getCurrentPosition`, ~20s interval)
  rather than `watchPosition`, trading a little latency for meaningfully
  less battery drain on a passenger's idle tab.

## 17. Push Notification Limitations

See the Browser Compatibility table above and the doc comment in
`apps/passenger/src/hooks/usePushNotifications.ts` — only foreground/local
notifications are implemented; true background Web Push needs a server-side
push sender this repo does not include.

## 18. Security Model

- **RLS everywhere** (`supabase/migrations/...007_rls.sql`): every table has
  RLS enabled; no table is left open by default.
- **Passenger identity**: real Supabase **anonymous auth**
  (`auth.signInAnonymously()`), so `auth.uid()` is a genuine, server-verified
  claim RLS can scope tickets to — with zero login UI shown to the user.
- **Conductor/Admin identity**: real Supabase Auth users; role stored in
  `profiles.role` and checked via `is_admin()`/`is_conductor()` SQL helper
  functions used throughout the RLS policies — never a frontend-only flag.
- **Server-side ticket creation**: `create_secure_ticket()` (SECURITY
  DEFINER RPC) recomputes fare from `fare_matrix`, re-validates the trip's
  stop progression, and generates the QR payload + HMAC signature — the
  client never supplies fare or status.
- **Ticket signing**: HMAC-SHA256 via `pgcrypto`, keyed by a secret stored
  only in the `app_secrets` table (no RLS policies at all — reachable only
  by SECURITY DEFINER functions and the service role).
- **Atomic validation**: `validate_ticket()` locks the ticket row
  (`SELECT … FOR UPDATE`) so concurrent/duplicate scans cannot both succeed.
- **Service-role key**: lives only in Supabase project secrets, used only by
  the `provision-conductor` Edge Function — never in any `apps/*` bundle.

## 19. Realtime Architecture

- **Broadcast** — GPS telemetry only, channel `room:route_<id>`, 3-5s
  throttle, never written to Postgres.
- **Presence** — conductor/bus online state, same channel; the Admin fleet
  map and passenger "waiting for GPS" state both key off Presence sync
  events, not off Broadcast alone.
- **Postgres Changes** — tickets, trips, trip_stops, trip_occupancy, alerts:
  anything persistent and comparatively low-frequency.

Full rationale: [ARCHITECTURE.md § Realtime Architecture](./ARCHITECTURE.md#realtime-architecture).

## 20. Troubleshooting

- **"Missing VITE_SUPABASE_URL…" at startup** — copy `.env.example` into the
  specific app's `.env`, not just the repo root.
- **RLS "permission denied" on writes** — confirm your admin account's
  `profiles.role = 'admin'` (see §5) and that a conductor's `user_id` is
  linked via `link_conductor_account`.
- **PostGIS functions fail on `db push`** — ensure your Supabase project
  plan supports the `postgis` extension (all current plans do); check
  `select postgis_version();`.
- **Camera scanner shows "unsupported"** — use a Chromium browser or ensure
  `@zxing/library` fallback isn't blocked by an ad-blocker/CSP.
- **QR payload rejected as "signature invalid"** — the `app_secrets` row was
  rotated after the ticket was issued; re-issue the ticket.

## 21. Rate Limiting & Scheduled Housekeeping

Part of the [scaling/operations plan](./SCALING_AND_OPERATIONS_PLAN.md), Phase 1.

### Database-level rate limits (already active, migration 016)

| RPC | Limit | Key |
|---|---|---|
| `create_secure_ticket` | 10 / 5 min | passenger's `auth.uid()` |
| `validate_ticket` | 60 / min | conductor's `auth.uid()` |
| `provision-conductor` (Edge Function) | 20 / hour | admin's `auth.uid()` |
| `find_nearest_stop` / `list_eligible_buses` | 60 / min | caller's `auth.uid()` (skipped if no session yet) |

Hitting a limit raises `RATE_LIMITED`, mapped to a friendly message via
`toAppError` like every other RPC error — no special client-side handling
needed. `rate_limit_events` (the backing table) is purged hourly by a
`pg_cron` job so it never grows large.

### ⚠️ Anonymous sign-ins must be explicitly enabled

**`external_anonymous_users_enabled` is `false` by default on a new Supabase
project.** Every passenger-facing feature — the entire zero-login ticket
flow — depends on `signInAnonymously()` succeeding, and it silently fails
with `anonymous_provider_disabled` until this is turned on. This was caught
live on this project by a load-test smoke run (`load-tests/`), not by code
review or `tsc` — the passenger app can look completely fine in the browser
right up until someone actually tries to buy a ticket. Enable it in
**Dashboard → Authentication → Providers → Anonymous Sign-Ins**, or via the
Management API:

```bash
curl -X PATCH "https://api.supabase.com/v1/projects/<ref>/config/auth" \
  -H "Authorization: Bearer <management-api-token>" \
  -H "Content-Type: application/json" \
  -d '{"external_anonymous_users_enabled": true}'
```

### Supabase Auth dashboard rate limits (manual — not covered by migrations)

Configure these explicitly in **Dashboard → Authentication → Rate Limits**
before going to production — the platform defaults are not tuned for a
zero-login flow where anonymous sign-in *is* the main traffic pattern:

- **Anonymous sign-ins per IP** — the main lever against someone scripting
  thousands of throwaway sessions to buy up all seats on a bus (the
  per-session `create_secure_ticket` limit above doesn't help if the
  attacker just mints a fresh session for each attempt).
- **Password sign-in attempts** (admin/conductor login) — tighten from
  default to reduce credential-stuffing exposure.

This is a project setting, not something a migration can express — it's
easy to forget on a fresh project, hence calling it out here explicitly.

### Anonymous auth user cleanup (migration 017)

A daily `pg_cron` job (`cleanup-stale-anonymous-users`, 3am UTC) deletes
anonymous `auth.users` rows that either never bought a ticket (48h old) or
whose tickets are all long-expired (90+ days). **It ships in dry-run mode**
— it only counts and logs to `cleanup_runs`, it does not delete anything,
until an operator deliberately enables it:

```sql
select cron.alter_job(
  (select jobid from cron.job where jobname = 'cleanup-stale-anonymous-users'),
  command => $$select cleanup_stale_anonymous_users(p_dry_run => false)$$
);
```

Review `select * from cleanup_runs order by ran_at desc limit 20;` for at
least a week of dry-run data before flipping this — this deletes real
`auth.users` rows and is not reversible.

### ⚠️ Operational lesson: default privileges are not enough on this project

Migration 015 tried to close a privilege gap by altering default privileges
for future functions. It didn't work — every function created afterward
(migration 016/017) still ended up callable by `anon`/`authenticated`
despite that ALTER, confirmed live via `has_function_privilege(...)` and
fixed in migration 018. The mechanism wasn't fully worth reverse-engineering
under time pressure; what's proven to actually work, empirically, on every
function in this schema without exception, is:

**Every new `SECURITY DEFINER` function must get an explicit
`revoke all on function <sig> from public, anon, authenticated;`
immediately after `create or replace function`, then an explicit
`grant execute ... to <only the intended roles>;`** — regardless of what
any `ALTER DEFAULT PRIVILEGES` statement claims should already be the case.
Migrations 018 and 019 both end with a `DO $$ ... raise exception ... $$`
block that calls `has_function_privilege()` against every new function and
fails the migration outright if the grant isn't what's intended — copy that
pattern for any future migration that adds a function anyone shouldn't be
able to call. Don't trust the grant statement alone; verify it live.

## 22. Data Lifecycle & Archival

Part of the [scaling/operations plan](./SCALING_AND_OPERATIONS_PLAN.md), Phase 2. Migration 019.

| Table | Retention | Mechanism |
|---|---|---|
| `tickets` | Terminal states only (`VALIDATED`/`EXPIRED`/`CANCELLED`) older than 18 months → moved to `tickets_archive`. `PAID`/`CREATED` are never touched at any age. | `archive_old_tickets()`, monthly `pg_cron`, **dry-run by default** |
| `alerts` | `RESOLVED` older than 1 year → moved to `alerts_archive`. `ACTIVE`/`ACKNOWLEDGED` are never touched at any age. | `archive_old_alerts()`, monthly `pg_cron`, **dry-run by default** |
| `cleanup_runs` (the audit log itself) | 1 year | `purge_old_cleanup_runs()`, monthly, not dry-run-gated (low-stakes audit-log hygiene) |

Both archival functions move rows with a single `WITH ... DELETE ... RETURNING` → `INSERT` statement (atomic — a row can never end up in neither table or both) and are gated by the same `cleanup_runs`-logged dry-run pattern as the anonymous-user job. Promote either to real archiving the same way:

```sql
select cron.alter_job(
  (select jobid from cron.job where jobname = 'archive-old-tickets'),
  command => $$select archive_old_tickets(p_dry_run => false)$$
);
```

`tickets_archive`/`alerts_archive` have RLS enabled with an admin-only read
policy — same access model as the live tables, just colder storage.
**Note for future reporting features**: nothing today queries ticket/alert
history across the archive boundary — a future admin history/reporting
page must query `tickets UNION tickets_archive` (and the equivalent for
alerts) to see the full picture once old rows start getting archived.

Partitioning `tickets` by month (making archival a cheap `DROP PARTITION`
instead of a `DELETE`) is intentionally **not** done here — deferred until
row count or query-latency data actually justifies it, per the scaling plan.

## 23. Load Testing

Part of the [scaling/operations plan](./SCALING_AND_OPERATIONS_PLAN.md), Phase 3. Full detail in [`load-tests/README.md`](./load-tests/README.md).

- `load-tests/k6/` — HTTP/RPC scenarios (ticket-purchase burst, duplicate-
  validation race, sustained read baseline). Needs the `k6` binary.
- `load-tests/realtime-harness/` — GPS Broadcast fan-out, using the real
  `@supabase/supabase-js` client (k6 doesn't speak the Realtime/Phoenix
  protocol). `npm install` then `node gps-fanout.js --subscribers=N`.

**Always smoke-test first** (`--vus 2 --iterations 2` or equivalent) before
scaling up — this caught two real, load-bearing bugs on this exact project
before they reached anyone:
1. `find_nearest_stop`/`list_eligible_buses` were marked `STABLE` after a
   rate-limit check (a write) was added inside them — PostgREST runs
   `STABLE` functions in a read-only transaction, so every call failed.
   Fixed in migration 020.
2. Anonymous sign-ins were disabled at the project level the whole time
   (see §21 above) — the passenger ticket flow had never actually been
   exercised end-to-end against this live project until a smoke test tried
   it and got `anonymous_provider_disabled`.

Neither was visible from reading the code. Don't skip the smoke-test step.

### Known gaps / explicitly deferred (documented, not hidden)

- **PNG PWA icons**: only SVG source icons are included (binary files
  cannot be produced as text) — see §13.
- **Background Web Push**: only foreground notifications are implemented —
  see §17.
- **pgTAP/integration tests for RPCs**: unit tests cover pure client logic;
  RPC atomicity/concurrency should be verified against a live Supabase
  instance (`supabase test db`) as a follow-up — see §11.
- **Razorpay real integration**: `MockPaymentProvider` is wired up;
  `RazorpayPaymentProvider` is a documented drop-in extension point, not
  implemented (real payment gateway credentials are out of scope for this
  repository).
